# Проверка производительности DefectBatch

Проверка проведена 22 ноября 2026 года на Windows: Node.js 24.14.0,
SQL Server Express, AMD Ryzen 7 5800H, 16 логических потоков, 32 ГБ памяти.
SQL, сервер приложения и клиент проверки работали на одном ПК.
Использовались отдельные временные базы: 250 смесей, 100 операторов,
журнал из 1 000, 10 000 и 50 000 синтетических записей с описаниями.
Рабочие записи и учётные данные не использовались.

## Результаты API

Время в миллисекундах. Повторные запросы — медиана пяти измерений.
«Проверка обновлений» после исправления возвращает 304 без тела, если данные
не изменились. До исправления интерфейс каждый раз запрашивал весь журнал.

| Записей | Повторная загрузка до | Полная повторная загрузка после | Проверка обновлений после | Размер полного ответа |
|---:|---:|---:|---:|---:|
| 1 000 | 98 | 33 | 9 | 0,6 МиБ |
| 10 000 | 675 | 139 | 17 | 5,7 МиБ |
| 50 000 | 3 033 | 648 | 64 | 28,6 МиБ |

При пяти одновременных запросах на 50 000 записей медиана полной загрузки
снизилась с 6 751 до 2 057 мс; проверка неизменившихся данных заняла 88 мс.
Это пять параллельных чтений от одного тестового пользователя, а не проверка
пяти независимых рабочих мест или длительный нагрузочный тест.

Первый запрос после изменения базы остался тяжёлым: для 50 000 записей
он занял 2,96 с до и 3,95 с после. Разница между одиночными холодными
измерениями не доказывает ускорение или регрессию: добавилась проверка
версии, а результат зависит от прогрева SQL и нагрузки компьютера.
Первичная передача полного журнала не устранена.

## Интерфейс

В браузере с 50 000 загруженных записей поиск SUP, фрагмента описания и смеси
дал соответственно 1, 1 и 200 результатов. Время выполнения перерисовки:

| Поиск | До, мс | После, мс |
|---|---:|---:|
| SUP | 133 | 34 |
| Фрагмент описания | 129 | 29 |
| Смесь | 110 | 21 |

После двух кадров браузера результаты были доступны за 41–49 мс.
Открытие страницы при уже прогретом снимке данных сервера заняло около
0,99 с. Это отдельный сценарий от холодного первого запроса API.
Проверены совместные фильтры линии и смеси, поиск смеси, переключение
страниц и очистка фильтров. Комбинация MB и PERF MIX 025 дала 67 записей;
сброс вернул 50 000.

Метрики интерфейса доступны при открытии `/?profile=1` в атрибутах `#page`:
`data-render-ms` — синхронная перерисовка; `data-paint-ms` — время до двух
кадров; `data-ready-ms` — время от навигации до первой готовой таблицы.
Это диагностические значения, а не точное измерение пользовательского
восприятия или гарантированный SLA.

## Что исправлено и что ограничивает рост

Сервер проверяет версию данных и повторно использует общий снимок, а браузер
не получает неизменившийся журнал снова. Проверка прав выполняется до
выдачи ответа; метка версии привязана к пользователю и роли. Ограниченный
список пользователей формируется отдельно и не изменяет общий снимок.
Поисковые строки строятся один раз при получении новых данных.

Полный экспорт 50 000 строк Excel занял 10,8 с до и 13,5 с после; файл —
около 3,1 МиБ. Экспорт не оптимизировался. Максимальная задержка цикла
обработки Node.js за весь сценарий достигла 7,3 с, включая экспорт.
Такая выгрузка может мешать другим запросам. Память общего процесса
сервера и тестового клиента достигала примерно 793 МиБ; это не отдельное
измерение памяти рабочего сервера.

Для дальнейшего роста нужны выдача страниц и фильтрация на сервере,
а также экспорт в отдельном процессе. Замена интерфейса на React сама
по себе эти ограничения не устраняет. Сравнение с отдельной реализацией
на React не проводилось, поэтому утверждать абсолютное равенство нельзя.

## Повторение

Установить зависимости и предоставить текущему Windows-пользователю доступ
к SQL Server с правом создания тестовых баз, затем выполнить:

```powershell
npm run benchmark
```

Команда создаёт собственную базу `DefectBatch_Test_Perf_<случайный ID>`,
запускает тестовый сервер на свободном порту и удаляет эту базу при штатном
завершении. Результат — `.local/performance/backend-report.json`.
При принудительном завершении процесса база может остаться: имя указанно
в `.local/performance/login.json`. Этот файл содержит временный тестовый
пароль, не должен публиковаться и удаляется при штатной очистке.
Не запускать нагрузочную проверку одновременно с рабочей пиковой нагрузкой.

При нестандартном экземпляре SQL задать `DB_SERVER` и `DB_DRIVER` в окружении
PowerShell. Скрипт намеренно сам задаёт случайный `DB_NAME` и не загружает
рабочий `.env`. Пять повторений и один экспорт на объём — короткая проверка;
значения p95 в JSON на такой выборке не являются статистической гарантией.

Автоматические проверки: 12 из 12 прошли, включая изоляцию ответов разных
ролей, отказ без авторизации, обновление меток после изменений и совпадение
результатов индексированного поиска с обычным.
