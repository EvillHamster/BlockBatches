# DefectBatch

Веб-приложение для учёта блокировок производственных партий: журнал контроля,
база смесей, справочники операторов и причин вылетов, пользователи и роли.

Интерфейс основан на оформлении [MixControl Version 1.4](https://github.com/EvillHamster/MixControl-Version-1.4),
исходный commit `375db0bd09c2772e7bee183ab2addcdfea97354a`.

## Из чего сделано приложение

| Часть | Используется |
|---|---|
| Интерфейс | HTML5, CSS, обычный JavaScript; без React, Vue и этапа сборки |
| Сервер | Node.js **24.x**, встроенный HTTP-сервер `node:http`, API `/api` |
| База данных | Microsoft SQL Server / SQL Server Express |
| Доступ к SQL | `mssql` **12.8.0** + `msnodesqlv8` **6.2.2**, Windows Authentication |
| Системный драйвер | Microsoft ODBC Driver **17** for SQL Server |
| Excel | `exceljs` **4.4.0**, импорт и экспорт `.xlsx` |
| Пароли | `node:crypto`, scrypt с отдельной солью |
| Вход | Случайные токены; в SQL хранится хеш токена; HttpOnly / SameSite=Strict cookie |
| Права | Общая матрица `dist/permissions.js`, проверка на сервере при каждом запросе |
| Проверки | Встроенный `node:test`, отдельные временные SQL-базы |

Точные версии зависимостей закреплены в `package-lock.json`.

**Для текущего варианта нужен Windows-сервер или постоянно включённый Windows-ПК.**
Проверенный вариант — Node.js 24 и SQL Server Express на одном компьютере.
Это приложение с сервером и SQL, а не статический сайт: GitHub Pages и загрузка
только папки `dist` не обеспечат его работу. Linux-хостинг потребует отдельной
адаптации подключения к SQL; в этой инструкции такой вариант не рассматривается.

## Возможности

- Журнал: создание, редактирование, удаление, поиск, фильтры и выбор видимых столбцов.
- SUP — строка ровно из 7 цифр с сохранением ведущих нулей.
- Все поля записи обязательны, кроме оператора. Линии: MB, FM, RW.
- Номера замеса, паллеты и образцов допускают целое число или диапазон `5-12`.
- Вес — неотрицательное число с точкой или запятой.
- Связь с исходным образцом для причины «Произведено из заблокированного MB».
- Поиск источника по любой линии; по умолчанию последние 7 календарных дней,
  старые записи доступны через «Показать за всё время».
- Ссылки `#record/ID` открывают карточку образца; «Назад» возвращает по цепочке.
- Справочники смесей, операторов и причин, защита связанных значений от удаления.
- Импорт Excel с предварительной проверкой, экспорт всех результатов фильтра.
- Управление пользователями, подтверждение паролей и переключатели показа пароля.
- Встроенная справка по роли: **F1** или **«Помощь · F1»**.

## Роли

| Действие | keyuser | Администратор | Инженер | Контроль качества | Сотрудник |
|---|---|---|---|---|---|
| Журнал, фильтры, столбцы, справка | Да | Да | Да | Да | Да |
| Создание и редактирование всех записей | Да | Да | Да | Нет | Да |
| Удаление отдельной записи | Да | Да | Да | Нет | Нет |
| Массовое удаление по фильтрам | Да | Да | Нет | Нет | Нет |
| Импорт | Да | Да | Да | Нет | Нет |
| Экспорт журнала | Да | Да | Да | Да | Нет |
| Управление смесями, операторами, причинами | Да | Да | Да | Нет | Нет |
| Управление пользователями | Да | Кроме keyuser | Нет | Нет | Нет |
| Изменение собственных имени, логина и пароля | Да | Да | Да | Да | Нет |

Роль в интерфейсе называется `keyuser`, код в базе — `KEYUSER`.
В системе ровно один keyuser: SQL-индекс и триггер запрещают второго,
удаление первого и снятие с него роли. Администратор не может менять его аккаунт.
Существующий keyuser при обновлении сохраняется.

Сотрудник может редактировать записи других пользователей и выбирать существующие
справочные значения, но не управляет справочниками и не добавляет значения из формы.
Пароль допускает **4–128 символов**, подтверждение обязательно. Два пустых поля
нового пароля при редактировании пользователя оставляют текущий пароль.

## 1. Подготовка своего сервера

Установите:

1. Windows Server или поддерживаемую Windows на постоянно включённом ПК.
2. **Node.js 24.x x64** с npm, с [официального сайта Node.js](https://nodejs.org/).
3. Git, если будете получать обновления через `git pull`.
4. Microsoft SQL Server Express / SQL Server и SQL Server Management Studio (SSMS).
5. **ODBC Driver 17 for SQL Server x64**. Название установленного драйвера должно
   совпадать с `DB_DRIVER` в настройках.

Проверьте Node.js и драйвер из PowerShell:

```powershell
node --version
npm --version
Get-OdbcDriver | Where-Object Name -Like '*ODBC Driver 17 for SQL Server*'
```

`node --version` должен показывать `v24...`.
Если установка `msnodesqlv8` сообщает о недостающих компонентах C++, проверьте
требования этой зависимости и установите соответствующий Microsoft Visual C++
Redistributable. Приложение не устанавливает системные драйверы автоматически.

### Учётная запись Windows и SQL

Приложение подключается к SQL **от имени Windows-пользователя, который запускает
процесс Node.js**. SQL-логин и пароль в `.env` не поддерживаются текущим кодом.

Для рабочего сервера заранее определите эту учётную запись. Если будете запускать
приложение через Планировщик заданий, проверяйте подключение именно под ней.

Два варианта подготовки базы:

- Приложение создаёт базу автоматически: учётной записи нужны права создания базы
  на SQL Server и изменения её структуры.
- Администратор SQL заранее создаёт базу `DefectBatch`, затем предоставляет
  Windows-учётной записи приложения доступ к ней. Для текущего механизма миграций
  нужны права на создание и изменение таблиц, индексов и триггеров внутри этой базы;
  роль `db_owner` в **этой отдельной базе** обеспечивает такие права.

При каждом запуске сервер проверяет структуру и применяет идемпотентные миграции
из `sql/001-schema.sql` … `sql/008-keyuser-guard.sql`.
Постоянные права администратора всего SQL Server для работы с уже созданной базой
не требуются. Учётная запись также должна иметь возможность подключиться к `master`,
где приложение проверяет наличие целевой базы.

Если SQL размещён на другом сервере, настройте Windows-аутентификацию и доступ
этой учётной записи на том SQL Server, сетевой протокол и межсерверный доступ.
Не открывайте SQL-порт пользователям сайта: браузеры обращаются только к Node.js.

## 2. Получение приложения и настройка

Пример размещения: `C:\Apps\DefectBatch`.
В PowerShell:

```powershell
New-Item -ItemType Directory -Path C:\Apps -Force
Set-Location C:\Apps
git clone https://github.com/EvillHamster/BlockBatches.git DefectBatch
Set-Location C:\Apps\DefectBatch
npm ci
Copy-Item .env.example .env
```

Если скачали ZIP с GitHub, распакуйте его так, чтобы в `C:\Apps\DefectBatch`
находились `package.json`, `server`, `dist` и `sql`, затем выполните `npm ci`.
Сборка интерфейса не нужна.

Откройте `.env` и укажите **свой** экземпляр SQL:

```dotenv
HOST=127.0.0.1
PORT=5173
DB_SERVER=localhost\SQLEXPRESS
DB_NAME=DefectBatch
DB_DRIVER=ODBC Driver 17 for SQL Server
COOKIE_SECURE=false
```

| Параметр | Значение |
|---|---|
| `HOST` | Адрес прослушивания: `127.0.0.1` только локально; `0.0.0.0` для прямого доступа по сети |
| `PORT` | Свободный порт приложения, по умолчанию `5173` |
| `DB_SERVER` | Реальное имя SQL-сервера и экземпляра, например `localhost\SQLEXPRESS` |
| `DB_NAME` | Имя отдельной базы; начинается с буквы, далее латинские буквы, цифры и `_`, до 64 символов |
| `DB_DRIVER` | Точное название установленного ODBC-драйвера; здесь проверен Driver 17 |
| `COOKIE_SECURE` | `true` для сайта с HTTPS; `false` для локального HTTP |

В `.env.example` указан пример `localhost\MIXCONTROL`. Это имя проверенного
экземпляра, а не обязательное имя для вашего сервера.
Не публикуйте рабочий `.env`, локальные пароли и резервные копии SQL в GitHub.

## 3. Первый запуск и вход

Из каталога приложения:

```powershell
npm run db:init
npm start
```

Откройте на сервере [http://127.0.0.1:5173/](http://127.0.0.1:5173/).
Окно с `npm start` оставьте открытым для пробной проверки.

При первом запуске, если keyuser ещё нет, сервер создаст **только первоначальный
аккаунт keyuser** и запишет случайный пароль в:

```text
.local/keyuser-bootstrap-<время>.txt
```

Точный путь появится в сообщении запуска. Войдите с данными из этого файла,
смените пароль в настройках и создайте остальных пользователей через интерфейс.
Существующий keyuser и его пароль не сбрасываются.

`npm run users:init` — дополнительная команда первоначальной подготовки четырёх
аккаунтов `keyuser`, `quality`, `admin`, `employer` со случайными паролями.
Для обычной рабочей установки она **не нужна**: дополнительные аккаунты лучше
создавать через раздел «Пользователи». Не запускайте её при каждом обновлении.
Её файлы паролей также находятся в `.local` и не входят в репозиторий.

Проверка подключения:

```powershell
Invoke-RestMethod http://127.0.0.1:5173/api/health
```

Ожидается `ok: True`, имя вашей базы и версия Node.js.
Проверьте вход, создание записи и сохранение данных после перезапуска приложения.

## 4. Доступ с других компьютеров в локальной сети

Если IIS и HTTPS пока не используются:

1. В `.env` установите `HOST=0.0.0.0`, `COOKIE_SECURE=false`.
2. Перезапустите приложение.
3. Разрешите входящий TCP-порт приложения в брандмауэре Windows для нужной сети.
4. На другом компьютере откройте `http://<IP-сервера>:5173/`.

Пример правила для доверенной локальной подсети, выполнять администратором
на сервере и только при необходимости:

```powershell
New-NetFirewallRule -DisplayName 'DefectBatch LAN' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 5173 -RemoteAddress LocalSubnet -Profile Domain,Private
```

`127.0.0.1` на другом компьютере означает **тот другой компьютер**, а не сервер.
Для доступа используйте IP или DNS-имя сервера. Вне доверенной сети используйте HTTPS.

## 5. Автозапуск после перезагрузки Windows

Для текущего приложения можно использовать встроенный **Планировщик заданий Windows**.
Сначала убедитесь, что ручной запуск под выбранной Windows-учётной записью работает.

1. Откройте «Планировщик заданий» → «Создать задачу», имя `DefectBatch`.
2. На вкладке «Общие» выберите Windows-учётную запись с доступом к SQL и каталогу
   приложения. Выберите выполнение независимо от входа пользователя в Windows.
3. Триггер — «При запуске системы»; можно добавить задержку 30–60 секунд,
   чтобы успела запуститься служба SQL Server.
4. Действие — «Запуск программы»:

   - Программа: `C:\Program Files\nodejs\node.exe`.
   - Аргументы: `--env-file="C:\Apps\DefectBatch\.env" "C:\Apps\DefectBatch\server\server.cjs"`.
   - Рабочая папка («Начать в»): `C:\Apps\DefectBatch`.

5. В параметрах включите перезапуск задачи при сбое и не допускайте запуск
   второго экземпляра, если задача уже работает.
6. Снимите ограничение «Останавливать задачу, выполняемую дольше …», чтобы сервер
   не завершался через несколько суток. Уберите условия питания/простоя,
   которые не подходят вашему серверу.
7. Сохраните задачу, укажите пароль Windows-учётной записи в системном диалоге,
   затем выполните задачу вручную и проверьте `/api/health`.
8. Перезагрузите сервер и повторите проверку с другого компьютера.

Учётная запись запуска должна иметь доступ на чтение к приложению и `.env`,
на запись — к `.local` для первоначального пароля. Если SQL находится на другом
компьютере, выбранный способ входа задачи должен позволять сетевую аутентификацию.
Не запускайте второй `npm start` одновременно с задачей: порт будет занят.

Описание параметров действия: [документация Microsoft](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtaskaction?view=windowsserver2025-ps).

## 6. Размещение с доменом и HTTPS через IIS

Схема: **браузер → HTTPS/IIS → HTTP на 127.0.0.1:5173 → Node.js → SQL Server**.
Node.js продолжает работать как отдельный процесс из предыдущего раздела.

1. Установите IIS, URL Rewrite и Application Request Routing (ARR).
2. Создайте отдельный IIS-сайт в корне домена, например `https://defectbatch.example.org/`,
   назначьте DNS и действующий TLS-сертификат.
3. В настройках ARR включите Proxy. Установите `preserveHostHeader=true`, чтобы
   до Node.js доходил исходный `Host`. Это нужно для проверки источника запросов.
4. Настройте правило URL Rewrite для всех путей на `http://127.0.0.1:5173/{R:1}`,
   сохраняя query string. Пример правила для конфигурации IIS-сайта:

```xml
<configuration>
  <system.webServer>
    <rewrite>
      <rules>
        <rule name="DefectBatch" stopProcessing="true">
          <match url="(.*)" />
          <action type="Rewrite" url="http://127.0.0.1:5173/{R:1}" appendQueryString="true" />
        </rule>
      </rules>
    </rewrite>
  </system.webServer>
</configuration>
```

5. В `.env` оставьте `HOST=127.0.0.1`, установите `COOKIE_SECURE=true` и
   перезапустите Node.js. За прокси этот параметр явно добавляет флаг `Secure`
   к cookie: приложение не доверяет входящему `X-Forwarded-Proto` автоматически.
6. Перенаправляйте HTTP на HTTPS на стороне IIS; разрешите внешним клиентам
   HTTPS-порт IIS. Порт Node.js `5173` и SQL не нужно выставлять в интернет.
7. Проверьте вход, сохранение записи, импорт/экспорт и ручной выход **по HTTPS-адресу**.

Размещайте приложение в корне отдельного сайта: текущий код использует абсолютные
пути `/api` и `/...js`. Подпапка вида `/defectbatch/` потребует изменения маршрутов.
`COOKIE_SECURE=true` не подходит для обычного HTTP по сетевому IP — браузер не будет
отправлять защищённую cookie по такому соединению.

Настройка IIS зависит от вашего сервера и здесь приведена как инструкция;
на этом рабочем ПК проверен прямой запуск Node.js, а не установка IIS.
Основа настройки: [Microsoft: reverse proxy с URL Rewrite и ARR](https://learn.microsoft.com/en-us/iis/extensions/url-rewrite-module/reverse-proxy-with-url-rewrite-v2-and-application-request-routing),
[Microsoft: сохранение Host в ARR](https://learn.microsoft.com/en-us/iis/extensions/configuring-application-request-routing-arr/arr-as-generic-proxy-in-hotmail-and-skydrive).

## 7. Обновление уже работающего сервера

1. Сделайте резервную копию SQL-базы и сохраните рабочий `.env`.
2. Остановите задачу `DefectBatch` в Планировщике или текущий процесс приложения.
3. Из папки приложения выполните:

```powershell
git pull --ff-only origin main
npm ci
npm run db:init
```

4. Запустите задачу / `npm start`, проверьте `/api/health`, вход и журнал.
5. При необходимости обновите страницу браузера с очисткой кэша.

Не перезаписывайте `.env` образцом при обновлении и не запускайте `users:init`
для восстановления вручную удалённых пользователей. Миграции сохраняют имеющиеся
записи и аккаунты. Если обнаружены несколько keyuser, миграция остановится:
нужно сначала разобрать конфликт учётных записей, а не автоматически удалять их.

Откат кода не откатывает схему SQL. При неудачном обновлении используйте совместимую
версию приложения и заранее сделанную резервную копию базы.

## 8. Данные и резервные копии

Основные таблицы: `Records`, `Mixtures`, `Users`, `Operators`, `Reasons`,
`Sessions`, `AppState`. SQL-база **не хранится в GitHub**.

- Настройте регулярное резервное копирование SQL через SSMS или SQL `BACKUP DATABASE`.
  Путь резервной копии должен быть доступен **службе SQL Server**, а не только
  пользователю, который открыл SSMS.
- При переносе на другой сервер восстановите базу SQL, перенесите `.env` с
  исправленным `DB_SERVER` и снова назначьте права Windows-учётной записи.
- ZIP с исходниками и Excel-экспорт не заменяют полную резервную копию SQL.
- Не включайте `.env`, `.local`, пароли, `.mdf`, `.ldf`, `.bak` и `node_modules`
  в коммиты. В проекте они исключены через `.gitignore`.

Сессии не имеют автоматического срока на сервере; браузерная cookie продлевается
при работе. Выход, смена пароля или удаление аккаунта прекращают соответствующие
сессии. Очистка cookie потребует нового входа.

## 9. Важные особенности

- Импорт `.xlsx`: до 5 МБ и 5 000 строк, без формул и макросов, с предварительной
  проверкой. Точные дубликаты пропускаются, существующие строки не перезаписываются.
- Excel журнала содержит «Исходная запись (ID)»: это ID уже существующего источника
  в той же базе; перенос ID между разными базами автоматически не выполняется.
- Архивные смеси остаются в истории. Новая запись из формы требует активную смесь;
  импорт исторических записей допускает архивные смеси.
- Ссылка на источник не может ссылаться на себя или образовывать цикл.
- Массовое удаление доступно только keyuser и администратору. Предварительный просмотр
  охватывает все страницы; без фильтров нужно ввести `УДАЛИТЬ ВСЁ`.
- При изменении ID/версий выбранных записей необходимо повторное подтверждение.
  Зависимости вне фильтра блокируют удаление. Операция выполняется одной транзакцией.
- Подтверждение удаления действует 10 минут; после перезапуска сервера нужен новый
  просмотр. Поэтому запускайте **один экземпляр Node.js**: несколько процессов
  за балансировщиком пока не поддерживаются этим механизмом подтверждений.
- Данные других клиентов обновляются примерно каждые 5 секунд; открытые формы
  защищены от перезаписи и используют проверку версии при сохранении.
- Настройки видимых столбцов и свёрнутого меню хранятся в браузере.

## 10. Проверки и структура проекта

```powershell
npm test
```

Нужен доступ к SQL Server под текущим Windows-пользователем и право создавать
тестовые базы. Тесты создают отдельные базы `DefectBatch_Test_<случайный ID>`
и удаляют только собственные тестовые базы. Рабочая база не очищается.

Проверяются роли и запреты API, защита keyuser, подтверждение и длина паролей,
изменение собственного профиля, CRUD, миграции, Excel, связи образцов, устаревшие
подтверждения, массовое удаление и конкурентные запросы.

```text
dist/                Интерфейс и общие правила/права
server/              HTTP API, авторизация, SQL, Excel, массовое удаление
sql/                 Последовательные миграции структуры
tests/               Автоматические проверки
.env.example         Пример настроек, не рабочие секреты
package.json         Команды и зависимости
package-lock.json    Зафиксированные версии зависимостей
serve.cjs            Совместимый запуск сервера
```
